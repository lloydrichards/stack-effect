# Catalog integration tests

- Keep catalog definition and registry validation in the catalog's own suite. When the promise concerns what a recipe generates through Scaffold, use a catalog integration suite. Official tooling, README, and Alchemy output tests live in [the official integration suite](../../../../catalogs/official-integration/test/Scaffold.test.ts).
- Use public Scaffold services with the real catalog and an isolated filesystem. Place suites that need both packages in a workspace that depends on both. Scaffold's tests already use the official catalog as a fixture, so adding Scaffold as an official catalog dependency would create a cycle.
- Assert the property the consumer relies on, such as a manifest entry, package export, documented link, deployment wiring, or preserved file bytes. If several source representations implement the same promise, assert the semantic property. Use a compile or runtime check when a file's presence alone cannot establish the behavior.
- For behavior that needs a generated project's dependencies or runtime, use the [catalog workspace workflow](../../catalog-workspace/SKILL.md) and the existing generated-project checks. Keep repository regressions and runnable fixtures outside generated targets and modules. Import the generated package's declared entry point when the catalog promises one. Keep supported install, type-check, and runtime combinations at their existing verification entry points.
- Run `bun run test --filter=@repo/catalog-official-integration`. The CLI check workflow selects this suite explicitly. When moving coverage, verify the new location remains selected by CI. See [catalog architecture](../../../../.okf/architecture/catalog.md#official-catalog-integration-tests).
