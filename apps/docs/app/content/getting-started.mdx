# Build your first Stack Effect project

Let us build your first Stack Effect app. We will start with an empty directory and finish with a React client calling an Effect HTTP API. Along the way, you will run the server, preview a second scaffold change, and review every change before Stack Effect writes it.

## 1. Create the workspace

Create a project named `my-app` with Stack Effect's defaults:

```bash
bunx stack-effect@latest init my-app --yes
```

`--yes` accepts the default project choices and runs the default finalize scripts without prompting. It also initializes a Git repository, stages the generated files, and creates an initial commit. Run `init my-app` without `--yes` when you want to choose the project configuration and review the finalize scripts interactively.

Enter the generated workspace:

```bash
cd my-app
```

Confirm that initialization left a clean repository with its first commit:

```bash
git status --short
git log -1 --format=%s
```

The first command should print nothing. The second should print:

```text
initial commit
```

Take a quick look around. `stack.effect.json` records the workspace choices, `package.json` contains the repository tasks, and `packages/config-typescript/` contains shared TypeScript configuration. There is no application yet, so let us add one.

## 2. Add an HTTP API

Start the interactive add flow from the workspace root:

```bash
bunx stack-effect@latest add
```

Follow this path through the prompts:

1. Choose **Server Application** as the target kind.
2. Enter `api` as the target name.
3. Select **HTTP API Server**.
4. Choose **Confirm all**.

At **Continue with these changes?**, review the resolved shape. It should contain the server and the domain API contracts that the server requires. This is the first checkpoint: Stack Effect has resolved the request, but has not planned repository writes yet.

Once you approve that shape, Stack Effect compares it with the repository. The Plan should look something like this:

At **Apply changes?**, confirm that the proposed paths contain no **needs merge** entries, then approve the change. After Apply finishes, the CLI reports what actually happened:

<AnsiTerminal

Keep the default finalize scripts selected when Stack Effect asks which commands to run.

You approve twice because the two prompts answer different questions: what should the project contain, and what will change on disk? [How Stack Effect changes your repository](/how-it-works) explains both checkpoints.

Once you approve those checkpoints and the setup commands finish, your first runnable application is ready.

## 3. Run the API

Start the generated workspace from its root:

```bash
bun dev
```

Wait for the server to report that it is listening on port 9000. Leave it running, open a second terminal in `my-app`, and request the root endpoint:

<AnsiTerminal
  title="my-app · API response"
  input={`\u001b[32m$\u001b[0m curl http://localhost:9000/
"Hello Effect!"`}
/>

Nice—you now have an Effect HTTP server responding locally.

Return to the first terminal and press Control-C to stop the development process before changing the scaffold again.

## 4. Preview a React client

The API works. Now preview a React client that calls it:

```bash
bunx stack-effect@latest add \
  --target client-react/web:client-react-http-api \
  --yes \
  --dry-run
```

The dry run shows the resolved client and its planned repository outcomes without writing files or running setup commands. You saw this Plan format when adding the server. This time, inspect it before anything is written and look for unexpected dependencies or **needs merge** entries.

Apply the same target without `--yes`, `--trust`, or `--dry-run`:

```bash
bunx stack-effect@latest add \
  --target client-react/web:client-react-http-api
```

This is the same target you just previewed, but now the command stops for approval. Review the Blueprint, review the Plan, and keep the default setup commands selected.

## 5. Verify the client and server together

Start the workspace again:

```bash
bun dev
```

Keep that terminal running and open [http://localhost:3000](http://localhost:3000) in a browser. Select **Call REST API**. The result should show:

```text
Message: Hello Effect!
Success: true
```

The button used the generated React client, shared API contract, and running server. Press Control-C in the terminal when you are finished.

## 6. Follow the generated request path

Before wrapping up, open these files to see how that request is assembled:

- `packages/domain/src/Api.ts` defines the API contract shared by client and server.
- `apps/server-api/src/index.ts` composes and starts the HTTP server.
- `apps/server-api/src/Api/Hello.ts` implements the response you observed.
- `apps/client-react-web/src/lib/atoms/hello-atom.ts` creates the typed client call.
- `apps/client-react-web/src/app.tsx` is the client composition root that brings the generated UI together.

The domain package owns the contract. The client uses it and the server implements it. You do not need to understand every Effect API here before you start changing the example.

## 7. Verify the repository

From the `my-app` root, run the generated checks:

```bash
bun run type-check
bun run lint
bun run build
```

Each command should exit successfully. The default workspace has no tests yet; these commands check its types, lint rules, and production build. You already checked the running application in the browser.

You now have the full first pass: scaffold a project, inspect the proposed changes, run the application, and check the result.
